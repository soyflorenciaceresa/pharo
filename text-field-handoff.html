00Resumen y API

Campo de texto de una línea con etiqueta y mensaje de ayuda para errores. En Figma solo hay una propiedad de variante (State) y tres propiedades de texto. Focus no es prop: se resuelve con :focus; Error se expresa con aria-invalid y error (ver Preguntas abiertas #1).

Combinaciones: Disabled gana sobre todo (sin foco, sin hover, sin validación). Focus + Error no existe en Figma (#3); sugerido: mantener el color de error y usar 2 px de ancho de borde, para que el foco siga siendo visible. ⚠️ Validar con diseño. Un campo con valor y sin foco (Filled) tampoco existe: usar --text-input-value con borde Default.

Focus: en un <input> de texto, :focus-visible y :focus coinciden siempre; usar :focus-visible. Transiciones: ⚠️ Pendiente, no hay tokens de motion. Sugerido: box-shadow, background-color, color 120ms ease-out, desactivado con prefers-reduced-motion: reduce.

05Comportamiento

  • Click en el label: mueve el foco al input (label for + id).
  • Focus: aplica el estado Focus. No hay cambio de layout ni scroll propio.
  • Escribir: el placeholder desaparece al primer carácter. Se emite onChange en cada cambio, sin debounce.
  • Validación: el componente no valida; quien lo usa pasa error y helperText. Recomendado validar en onBlur y al enviar, no en cada tecla. Al corregirse el valor, quitar el error en el siguiente onChange [Supuesto — validar].
  • Error: aparece el helper y se enlaza con aria-describedby. El alto total pasa de 54 a 72 px (desplaza el contenido siguiente).
  • Disabled: no recibe foco ni eventos, y no se envía en formularios nativos. Cursor not-allowed [Supuesto — validar].
  • Enter: dentro de un <form> con botón de envío, envía el formulario (comportamiento nativo).
  • Controlado vs. no controlado: soportar ambos (value + onChange, o defaultValue). Por defecto, no controlado.
  • Eventos que expone: onChange(e), onFocus(e), onBlur(e). Expone ref al <input>.
  • Timings: no hay delays ni animaciones definidas. ⚠️ Pendiente (ver Estados → Transiciones).

07Reglas responsive

El componente no cambia de patrón entre breakpoints. Breakpoints supuestos: mobile < 768, tablet 768–1023, desktop ≥ 1024. ⚠️ Pendiente confirmar los del sistema (#10).

BreakpointCambios
MobileWidth fill. Alto recomendado 44 px y font-size del input ≥ 16 px (por debajo, iOS Safari hace zoom al enfocar). [Supuesto — validar con diseño]
TabletWidth fill del contenedor; sin cambios de estilo.
DesktopWidth fill del contenedor (280 px por defecto en Figma); sin cambios de estilo.

No se ocultan ni reordenan partes. El label siempre va encima del campo.

09Composición y componentes átomo

ComponenteUsado en parteProps / variante usadaPara qué
———No usa componentes anidados: en Figma son solo capas de texto y un frame. No reimplementar label ni helper como componentes aparte; viven dentro del Text field.
Icon—No aplicaNo hay ícono leading, trailing ni de error (#11).

Dónde se usa: en formularios, dentro de Form Container [Supuesto — validar]. El contenedor define el espacio entre campos; el Text field no agrega margen externo. Props que se pasan hacia abajo desde un formulario: name, value, onChange, error, helperText, disabled.

Preguntas abiertas

  1. API de Error: ¿se expone como error boolean o como error: string (el mensaje)? En Figma es una variante + prop de texto.
  2. Placeholder vs valor: Figma usa una sola prop Value; proponemos separar placeholder (Default) de value.
  3. Estados faltantes: Hover, Filled (con valor sin foco) y Focus + Error.
  4. Read-only y Loading: ¿aplican? Hoy no existen.
  5. Alto: 36 px actual vs 44 px recomendado para táctil.
  6. Contraste: borde Default (1,3:1) y placeholder (2,0:1) no cumplen AA.
  7. Ancho: ¿fill con min/max o 280 px fijo?
  8. Label largo: ¿wrap, truncado o límite de caracteres?
  9. Obligatorio y contador: no hay indicador de campo requerido ni contador de caracteres.
  10. Breakpoints y motion: confirmar breakpoints del sistema y tokens de transición.
  11. Íconos y helper informativo: ¿habrá ícono de error, botón de limpiar o helper en estados no error?
